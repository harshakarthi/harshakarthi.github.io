Automation · Software Engineer

Automating manual letter intake

7–10Kletters a day
5–8 minmanual effort per letter, removed

The problem

The letter intake was fully manual. Each letter's details had to be entered into the NGS screens, reviewed and submitted individually, with thousands of letters processed every day at 5–8 minutes per letter.

What I did

  • Used the source system's database view to retrieve the letter data directly, instead of having it entered manually.
  • Built a background job that reads each template's data mapping from the database, uses it to pull the letter data from the view, and submits the letter into NGS.
  • Because the mappings are stored as configuration, the same job handles all 300+ letter templates without code changes.
  • Connected the automated submission to NGS's existing workflow, so the letters continued through the same downstream process without changes.

The result

Between 7,000 and 10,000 letters a day are now created automatically, saving 5–8 minutes of manual work on each one. Because the data comes straight from the source system, there are no manual entry errors.

Cloud · Software Engineer, 2026

Windows VMs to Microsoft Azure

7 → 1config databases
1App Service setup for all tenants
AZ-900certified during the project

The problem

NGS was moving from Windows VMs to Microsoft Azure. Once the migration started, it became clear that giving each Line of Business its own App Service would make the hosting costs too high. We needed a way to run all of them more cheaply on Azure.

What I did

  • Proposed consolidating the seven per-client configuration databases into one shared multi-tenant database, and carried out the change once it was approved.
  • Changed identity keys to composite keys with a tenant ID, and identified the tenant from each request's URL so one API setup could serve every client. Transaction databases stayed separate.
  • Updated the background processes to run as jobs on Azure, and changed both the API and the jobs to read connection details from Azure Key Vault.
  • Applied database changes through scripts and validated them with test scripts and manual testing of business-critical flows.

The result

All tenants now run from a single App Service setup, which reduced Azure infrastructure cost and simplified deployments.

Production support · Software Engineer

Tracking down a memory problem

~16%CPU while memory climbed
1root cause: the rule engine

The problem

After the move to Azure, the APIs slowed down. Memory was high while CPU sat at around 16%, so the usual suspects did not explain it.

What I did

  • Used Application Insights metrics to narrow the issue down, and traced it to Roslyn holding memory inside the rule engine.
  • Put in metric-based rolling API restarts as a short-term fix to protect users.
  • Replaced the direct C# code in rules with rule extensions, removing the cause.

The result

The platform stopped degrading over time, and the stopgap restarts were no longer needed.

Modernisation · Associate Software Engineer II, 2023–2024

.NET 6 to .NET 8 upgrade

36projects upgraded
6 → 8.NET Version

The problem

The platform's background processing ran as 36 separate .NET 6 console applications that generate letters. .NET 6 was reaching end of support, and the PDF generating library used, iTextSharp, was no longer supported.

What I did

  • Upgraded all 36 projects to .NET 8.
  • Replaced the unsupported libraries, including swapping iTextSharp for PDFsharp for PDF generation.

The result

The upgrade was completed before .NET 6 reached end of support, so letter generation now runs on a supported runtime and supported libraries.
